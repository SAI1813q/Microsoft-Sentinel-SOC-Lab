
# 🤖 Playbooks & Automation

## 📖 Overview

Microsoft Sentinel Playbooks and Automation Rules extend the capabilities of a traditional SIEM by introducing **Security Orchestration, Automation, and Response (SOAR)**. They automate repetitive incident response tasks, reduce manual effort, and ensure security events are handled consistently according to predefined workflows.

This project implements both **Microsoft Sentinel Automation Rules** and **Azure Logic Apps** to automate incident triage and analyst notification. Automation Rules are used to update incident properties, assign owners, and add contextual information, while Logic Apps provide external notifications and integrate Microsoft Sentinel with other services.

Each automation documented below includes its purpose, configuration, execution workflow, validation, and supporting screenshots.

# ⚙️ User Added to Local Administrators

## 📖 Overview

This Microsoft Defender **Enhanced Automation Rule** automatically triages high-priority privilege escalation alerts generated by Microsoft Sentinel. When the **User Added to Local Administrators** analytics rule creates an alert, this automation immediately updates the alert status and assigns it to the designated Tier 3 SOC analyst for investigation.

By eliminating manual alert assignment, the automation ensures that privilege escalation incidents are acknowledged, prioritized, and routed to the appropriate analyst as soon as they are detected.

---

## 🎯 Purpose

This automation was implemented to streamline the initial triage of privilege escalation incidents and improve the efficiency of the Security Operations Center (SOC).

Its primary objectives are:

- Automatically identify high-priority privilege escalation alerts.
- Immediately update the alert status to **In Progress**.
- Automatically assign the alert to the designated Tier 3 SOC analyst.
- Reduce manual triage effort and ensure consistent incident handling.

---

## ⚡ Trigger

The automation is configured to execute whenever a **new alert is created** within Microsoft Defender. It continuously monitors newly generated alerts and evaluates whether they match the configured analytics rule.

| Setting | Value |
|---------|-------|
| Trigger Event | When a new alert is created |
| Alert Source | Microsoft Sentinel Analytics Rule |
| Target Alert | **User Added to Local Administrators** |
| Execution Scope | All current and future Microsoft Sentinel workspaces |

---

## 🔍 Conditions

Before executing any automated action, the rule evaluates the following condition:

| Condition | Value |
|-----------|-------|
| Analytic Rule Name | **User Added to Local Administrators** |

If the alert matches the configured analytics rule, the automation proceeds to execute the predefined actions.

---

## ⚙️ Automated Actions

When all conditions are satisfied, the automation performs the following actions automatically:

| Action | Value |
|---------|-------|
| Update Alert Status | **In Progress** |
| Assign Alert | Designated Tier 3 SOC Analyst |
| Rule Expiration | Indefinite |

---

## 🔄 Automation Workflow

```text
            │

            │

            │

            ▼

            │
            ▼

            │
            ▼
Alert Assigned to Tier 3 SOC Analyst
```

- No manual analyst interaction was required during the triage process.

This successful validation confirms that the automation functions as expected and consistently performs the configured incident triage actions.

# ⚙️ Auto-Close Known IP Addresses (VPN)

## 📖 Overview

This Microsoft Defender **Standard Automation Rule** automatically closes Microsoft Sentinel incidents generated by the **Impossible Travel** analytics rule when the detected IP address matches a trusted corporate VPN address.

By automatically identifying known trusted IP addresses, the automation reduces false positives and prevents analysts from spending time investigating expected user activity.

---

## 🎯 Purpose

This automation was implemented to reduce unnecessary analyst workload by automatically handling expected authentication events originating from trusted corporate VPN infrastructure.

Its primary objectives are:

- Automatically identify incidents generated by the **Impossible Travel** analytics rule.
- Verify whether the detected IP address belongs to the approved corporate VPN.
- Automatically close benign incidents.
- Apply an appropriate incident classification.
- Document the reason for closure for future auditing.

---

## ⚡ Trigger

The automation is configured to execute whenever a **new incident is created** within the **LAW-Project1** Microsoft Sentinel workspace.

| Workspace | LAW-Project1 |

---

| Condition | Value |
|-----------|-------|
| Group Operator | AND |
| Analytic Rule Name | Contains **Impossible travel** |
| IP Address | Equals **182.68.12.54** |

The automation executes only when **both** conditions are satisfied.

# 📧 Logic App Summary: Email Notification

---

## 📖 Overview

This Azure Logic App provides automated email notifications for Microsoft Sentinel alerts. The playbook is triggered through a Microsoft Sentinel Automation Rule whenever a matching alert is generated, ensuring SOC analysts receive immediate notification without continuously monitoring the Microsoft Sentinel portal.

---

## 🎯 Purpose

- 🚨 **Real-Time Alert Notification:** Immediately notify SOC analysts when selected Sentinel alerts are generated.
- ⚡ **Reduce Response Time:** Minimize the delay between threat detection and analyst awareness.
- 📋 **Provide Alert Context:** Include key alert details within the email to support rapid triage.
- 🤖 **Demonstrate SOAR Integration:** Showcase end-to-end automation using Microsoft Sentinel, Azure Logic Apps, and Outlook.

---

## ⚡ Trigger

The Logic App is executed by a Microsoft Sentinel Automation Rule with the following configuration:

- **Trigger:** When alert is created
- **Condition:** Analytic Rule Name contains **Firewall Disabled**
- **Action:** Run Logic App **Notification**

Only alerts generated by the **Firewall Disabled** analytic rule invoke this playbook.

---

## 🔄 Workflow

```text
Firewall Disabled Analytic Rule
                │
                ▼
Microsoft Sentinel Alert Created
                │
                ▼
Automation Rule Triggered
                │
                ▼
Run Logic App (Notification)
                │
                ▼
Microsoft Sentinel Alert Trigger
                │
                ▼
Extract Alert Properties
                │
                ▼
Generate Email
                │
                ▼
SOC Analyst Receives Notification
```

---

## ⚙️ Logic App Configuration

The Logic App consists of two workflow components.

### 1️⃣ Microsoft Sentinel Alert Trigger

The workflow begins with the **Microsoft Sentinel Alert** trigger, which receives alert data from the associated Automation Rule whenever the specified analytic rule is triggered.

### 2️⃣ Send Email (V2)

The **Send an email (V2)** action uses dynamic content from the alert payload to generate an Outlook email containing:

- 📝 Alert Name
- 🚨 Severity
- 📄 Description
- 🕒 Alert Time

This enables analysts to quickly understand the incident without opening the Microsoft Sentinel portal.

---

## 📧 Email Template

Each notification email contains the following information:

| Field | Description |
|--------|-------------|
| 📝 Alert Name | Name of the generated Sentinel alert |
| 🚨 Severity | Alert severity level |
| 📄 Description | Detection description |
| 🕒 Time | Alert generation timestamp |

The email concludes with a message indicating that it was automatically generated by the Microsoft Sentinel Logic App.

---

## ✅ Validation

# 🚨 Automated Containment Recommendation

## 📖 Overview

This Azure Logic App provides automated incident enrichment for Microsoft Sentinel incidents by extracting affected account and host entities and adding a standardized containment recommendation as an incident comment.

The playbook is designed to support SOC analysts during the initial triage phase by providing immediate context about the affected identity and endpoint, along with recommended containment actions.

> ⚠️ **Important:** This playbook does **not** automatically disable user accounts or isolate endpoints. It provides recommendations only and requires SOC analyst validation before any containment action is performed.

---

## 🎯 Purpose

This playbook was implemented to improve incident triage and provide standardized containment guidance for security incidents.

Its primary objectives are:

* 👤 Identify the affected account associated with the incident.
* 💻 Identify the affected host or endpoint.
* 📝 Automatically add a structured investigation comment to the incident.
* 🚨 Provide recommended containment actions to the SOC analyst.
* 🛡️ Prevent unauthorized automated containment by requiring analyst validation.
* ⚡ Reduce manual effort during initial incident investigation.

## 🔍 Entity Extraction

The workflow uses Microsoft Sentinel entity actions to extract contextual information from the incident.

| Entity | Action | Purpose |
| --- | --- | --- |
| 👤 Account | `Entities - Get Accounts` | Identifies the affected user/account |
| 💻 Host | `Entities - Get Hosts` | Identifies the affected endpoint |
| 📝 Incident | `Microsoft Sentinel Incident` | Provides the incident context |

### 👤 Account Entity

The `Entities - Get Accounts` action extracts account entities associated with the incident.

Example: `ROOT\SecManager`

### 💻 Host Entity

The `Entities - Get Hosts` action extracts host entities associated with the incident.

Example: `Vm1.root.project`

---

## ⚙️ Logic App Workflow

The Logic App consists of the following workflow stages:

### 1️⃣ Microsoft Sentinel Incident Trigger

The workflow begins when a new Microsoft Sentinel incident triggers the Logic App.

The incident context provides the information required for subsequent entity enrichment.

### 2️⃣ Get Account Entities

The `Entities - Get Accounts` action extracts account entities associated with the incident.

The returned account information is used to identify the potentially affected user or identity.

### 3️⃣ Get Host Entities

The `Entities - Get Hosts` action extracts host entities associated with the incident.

The returned host information identifies the endpoint associated with the security event.

### 4️⃣ Compose Incident Context

The Compose action processes and formats the retrieved account and host information for inclusion in the incident comment.

### 5️⃣ Entity Processing

The workflow processes the returned entity information using `For each` actions where required.

This allows the playbook to handle incidents containing multiple account or host entities.

### 6️⃣ Add Comment to Incident

The `Add comment to incident (V3)` action adds the structured containment recommendation directly to the Microsoft Sentinel incident.

## 📝 Automated Incident Comment

The Logic App automatically adds a standardized containment recommendation to the incident.

The generated comment contains:

* 🚨 Automated Containment Recommendation
* 👤 Affected account
* 💻 Affected host
* 🔍 Recommended SOC investigation actions
* 🛡️ Analyst validation requirement

The recommendation includes:

**🚨 AUTOMATED CONTAINMENT RECOMMENDATION**

This incident requires SOC investigation.

**Recommended Actions:**

1. Review the affected account for possible compromise.
2. Review the affected endpoint for malicious activity.
3. Consider disabling the affected account if compromise is confirmed.
4. Consider isolating the affected endpoint if malicious activity is confirmed.
5. Review authentication activity and related security alerts.
6. Investigate additional indicators associated with the incident.

**👤 Affected Account:** `<Account Entity>`

**💻 Affected Host:** `<Host Entity>`

**⚠️ NO AUTOMATED CONTAINMENT ACTION WAS EXECUTED.**

Account and endpoint containment require SOC analyst validation.

Generated automatically by Microsoft Sentinel SOAR workflow.

---

## 🛡️ Safety & Analyst Validation

This playbook intentionally does **not** perform automatic containment.

The Logic App only provides contextual recommendations to the SOC analyst.

The following actions require analyst validation:

| Recommended Action | Execution |
| --- | --- |
| Review affected account | 👨‍💻 SOC Analyst |
| Disable compromised account | 👨‍💻 SOC Analyst |
| Isolate affected endpoint | 👨‍💻 SOC Analyst |
| Review authentication activity | 👨‍💻 SOC Analyst |
| Investigate related alerts | 👨‍💻 SOC Analyst |

This design prevents potentially legitimate users or endpoints from being automatically disabled or isolated due to a false positive.

---

## 🔐 Human-in-the-Loop Response

The workflow follows a human-in-the-loop response model:

**Detection → Incident Creation → Entity Enrichment → Containment Recommendation → SOC Analyst Validation → Manual Containment**

This approach allows the SOC analyst to validate the incident before performing potentially disruptive actions such as account disabling or endpoint isolation.

## 🚀 Future Enhancement

The current implementation intentionally stops at recommendation and analyst validation.

A future version could extend the workflow with controlled containment actions such as:

**Incident → Entity Enrichment → Risk / Detection Validation → SOC Approval → Disable Compromised Account / Isolate Compromised Endpoint**

This would allow the workflow to evolve from **incident enrichment and response guidance** into a controlled automated containment workflow when the required licensing and permissions are available.
